## 1. 心智模型①：自动驾驶软件栈

### 1.1 经典四段栈：感知 → 预测 → 规划 → 控制

```
观测(传感器) ─► 感知 Perception ─► 预测 Prediction ─► 规划 Planning ─► 控制 Control ─► 动作(油门/刹车/方向)
                 "周围有什么"        "它们要去哪"        "我该怎么走"      "怎么执行"
```

- **感知 Perception**：检测/分割/跟踪——把像素变成「物体 + 位置 + 速度」。
- **预测 Prediction**：预测其他交通参与者未来轨迹/意图（行人会不会横穿？）。
- **规划 Planning**：在预测之上决定自车行为（让行 / 变道 / 减速），分行为决策（behavior）与轨迹规划（trajectory/motion）。
- **控制 Control**：把规划出的轨迹/动作变成具体 `throttle/steer/brake`，要稳、不抖。

> 本项目分工：**VLA 承担「感知+预测+高层规划」**（看图 + 读中文指令 → 输出一个高层动作），**传统控制器承担低层控制**（高层动作 → `VehicleControl`）。

### 1.2 关键转变：闭环（closed-loop），不是一次前向

你训练 DNN 是 **一次性前向**：`数据集 → 预测 → 算 loss`，样本之间 **i.i.d.**。
自动驾驶是 **闭环**：

```
   o_t ─► π(策略) ─► a_t ─► 环境 f ─► o_{t+1} ─► π ─► a_{t+1} ─► ...
         ▲                                              │
         └────── 你这一步的动作改变了下一步看到的世界 ◄────┘
```

后果（对 DL 人最重要的一点）：**你自己的动作会改变未来输入的分布**。开偏一点 → 看到训练时没见过的画面 → 偏得更多。这就是 **分布漂移 / 复合误差**（[§4.4](#44-分布漂移与复合误差界) 给出数学界）。监督学习里被 i.i.d. 假设藏起来的问题，在闭环里全部暴露。

### 1.3 三种范式（"自动驾驶模型"到底指什么）

| 范式                                | 结构                                                    | 代表                     | 优点 / 痛点                                              |
| ----------------------------------- | ------------------------------------------------------- | ------------------------ | -------------------------------------------------------- |
| **模块化 pipeline**           | 感知/预测/规划/控制各自独立模块（可各用 DL 或经典算法） | Apollo / Autoware        | 可解释、可单测；但模块间误差传递、接口笨重               |
| **端到端 E2E**                | 传感器 → 直接出控制，一个网络                          | PilotNet (Bojarski 2016) | 简单、数据驱动；但黑箱、数据饥渴、闭环难（§5.2）        |
| **分层 / 语义高层**（本项目） | 大模型出**高层语义动作**，经典控制器执行低层      | DriveVLM / 本项目        | 解耦语义推理与控制，动作空间小、好调试；受大模型延迟约束 |

**VLA（Vision-Language-Action）**= 把视觉语言大模型当「驾驶大脑」：看图像 + 读中文指令 → 推理出高层动作。它天然适合「分层」范式的上层。

## 2. 心智模型②：CARLA 运行机制

### 2.1 server-client + 游戏引擎

```
┌───────────────────────┐      localhost:2000       ┌──────────────────────────┐
│   CARLA server         │ ◄───────────────────────► │  你的 Python client       │
│  (CarlaUE4，UE4 引擎)   │   spawn / 挂传感器 / tick   │  (health_check.py 等)     │
│  虚拟世界：路·车·人·     │                            │                          │
│  物理·光照·渲染          │ ── 传感器数据(渲染图像) ──► │  numpy → 决策 → 控制       │
└───────────────────────┘                            └──────────────────────────┘
```

要刻进脑子的四点：

1. **两个进程**。server 是吃显存、开窗口的大程序；client 是你的小脚本，通过 `:2000` 通信。
2. **版本必须一致**：client wheel 与 server 都得是 0.9.16，否则报错诡异。
3. **传感器拍的是引擎渲染的虚拟世界**——没有真实相机；depth / semantic 是引擎直接给的 **ground truth**（不是估计值）。
4. **时间由谁推进**？见 §2.2。

### 2.2 异步 vs 同步（先建立概念，第二课细做）

- **异步**：server 自己按 wall-clock 跑，不等 client。client 拿到的是「最近一帧」，**帧率不稳、不可复现**。
- **同步**：`settings.synchronous_mode=True`，server **等你调 `world.tick()`** 才推进一步，配合 `fixed_delta_seconds=0.05`（=20 FPS）。**数据可复现、传感器对齐的命门**（[§4.2](#42-离散时间动力学与固定步长)）。

> 第一课先用默认（异步）把世界跑起来、连上、看信息即可；同步留到第二课。

### 2.3 一切皆 actor

CARLA 里车、人、传感器、交通灯都是 **actor**。生命周期统一：

```
blueprint(蓝图/模板) ──► world.try_spawn_actor(bp, transform) ──► actor(实体) ──► actor.destroy()
```

**不 destroy 会残留**，下次 spawn 可能因占位失败——必须写统一 `cleanup()`（[§6.2](#62-actor-生命周期与-cleanup)）。

### 2.4 世界是「运行时动态搭建」的，不是预先打包

常见误解：以为要先把场景写死、再启动 server。实际相反：

- **server 启动后只是一个空的通用模拟器**（加载某张 Town，提供世界 + 物理 + 渲染）。
- **场景由 client 脚本在运行时搭出来**：运行中 spawn 行人/车/二轮 → 挂传感器 → 发控制 → `world.tick()` → 跑完 `cleanup()`。
- **改脚本再跑，server 不用重启**（换地图用 `load_world` 重载世界，进程仍在）。

```
启动 server(一次,常开) → 跑 client 脚本(运行时 spawn + 控制 + tick) → cleanup → 改脚本再跑
```

⟹ 所以「场景定义 = 脚本代码」（哪个 seed、spawn 哪些 actor、触发条件），不是 server 里的静态文件。这就是阶段 2「场景生成」要做的事，也是为什么必须写 `cleanup()`（运行时加进去的东西得自己清）。

> **同步模式顺带吸收 API 延迟**：同步下 server 会**停下来等你**调 `tick`，仿真时间与墙上时钟解耦（每 tick 恒等于 `fixed_delta_seconds` 仿真秒）。所以 VLA/API 推理慢只让墙上时钟变慢，**车的决策时机完全正确**（详见 [§5.5(5)](#5-必须知道的深度学习原理)）。

### 2.5 传感器：CARLA 给什么、本项目用什么

CARLA 的传感器**不止摄像头**，且都是挂在车上的子 actor：

| 类别 | 传感器                                                                    | 给什么                                                                                 |
| ---- | ------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 相机 | RGB /**深度** / **语义分割** / 实例分割                       | RGB 是 2D 照片（无深度）；深度相机每像素给真距离（引擎真值）；语义相机每像素给类别真值 |
| 测距 | **LIDAR** / **RADAR**                                         | 激光给点云距离；雷达直接给距离 + 速度                                                  |
| 其他 | GNSS / IMU / 碰撞 / 压线 /**障碍物检测**(`sensor.other.obstacle`) | 障碍检测直接报前方最近障碍距离                                                         |

- **本项目选型**（PROJECT_PLAN §5.1）：前视 RGB（必须）+ 可选左右后 + 深度 + 语义；**几个相机由你定**。
- **关键分工**：**VLA 用 RGB 做语义推理**；**安全层算 TTC 用深度/雷达/障碍检测**（几何量，比图像识别又快又准，[§5.3.1](#531-高层动作--控制器映射表与应急归属)）。
- 深度/语义相机是仿真"作弊福利"（真车要靠算法估，CARLA 直接给真值）——早期开发很方便，但**报告里要说明哪些来自真值**。

## 3. 心智模型③：鬼探头 = 一个 POMDP

```
行驶方向 →
──────────────────────────────────────────────
      🚌 公交(遮挡物)
      🚶 ← 行人藏在公交后，自车相机看不见(=不可观测状态)
──────────────────────────────────────────────
 🚗 ego ……(进入触发距离)……💥 行人在极短 TTC 内窜出
```

- **难点一句话**：「**看不见也要会提前减速**」。
- **本质**：被遮挡的行人是 **不可观测的隐藏状态**。所以鬼探头不是 MDP（状态全可见），而是 **POMDP**（部分可观测，[§4.3](#43-闭环--pomdp-形式化)）。
- **为什么纯感知失败**：检测器「看见了才反应」，但关键物体被遮挡 → TTC 太短，物理上来不及（[§4.5](#45-ttc鬼探头的核心量)）。
- **VLA + 中文指令的价值**：指令（"注意公交车后可能有行人，确认安全再通过"）相当于给模型注入 **关于隐藏状态的先验/belief**——把"这里可能有人"变成可执行的预防性减速。这正是大模型常识推理胜过纯检测器的地方。

### 3.1 三层「状态」：为什么纯检测器写不进去

| 符号    | 名字                  | 鬼探头里是什么                                       |
| ------- | --------------------- | ---------------------------------------------------- |
| $s_t$ | **真实状态**    | 含公交车后那个行人（客观存在）                       |
| $o_t$ | **观测**        | 相机像素——**里面没有行人**（被挡住，零信号） |
| $b_t$ | **信念 belief** | "这后面有人的概率"——推理出来的                     |

检测器的工作是 $o_t \to s_t$ 里**看得见的部分**。被遮挡的行人在 $o_t$ 里一个像素都没有 → 检测器**没有输入信号可检测**。这不是检测器不够好，是**物理上无对象可检**。所以你**无法把鬼探头"写进检测器"**。"可能有人"只能来自 $o_t$ 之外的**先验**：要么**写死规则**（不泛化，对应阶段 3 的 rule baseline），要么**常识推理**（VLA + 中文指令，泛化）。中文指令在数学上就是注入 $b_t$ 的外部先验（[§4.3](#43-闭环--pomdp-形式化)）。

### 3.2 特权信息红线：什么能喂给决策层，什么不能

鬼探头实验是否公平，全看你**喂给 VLA 决策层的输入**有没有"视线穿透"：

| 信息                                               | 能否喂给决策层 | 为什么                                          |
| -------------------------------------------------- | -------------- | ----------------------------------------------- |
| 地图/车道/路线（**waypoint**）、ego 自身状态 | ✅ 能          | 真车也有高精地图 + GPS + 自车传感器，是合法先验 |
| 视野内**可见** actor 的位置/速度             | ✅ 一般可      | 相当于"完美感知"的简化                          |
| **被遮挡 actor 的真值**（公交车后那个行人）  | ❌ 不能        | 等于"透过公交车看人"，直接摧毁 POMDP 难点       |

> ⚠️ PROJECT_PLAN §5.1 把「周围 actor metadata」列为输入——早期原型可以，但**做鬼探头评测时必须过滤掉被遮挡的 actor**，否则模型直接"看见"了。
>
> **关于安全层用真值算 TTC**：对**可见**前车用真值 ≈ 真车的雷达，可接受；但对**被遮挡**目标用真值，无论哪一层都是作弊（雷达也穿不透公交车）。红线的本质：**不让任何模块获得"视线穿透"的信息。**

## 4. 必须知道的数学原理

> 这一节是第一课真正"硬"的部分。坐标变换在挂传感器、设 spawn 点、移 spectator 时天天用；MDP/误差界决定了你为什么要这么设计模型。

### 4.1 坐标系与刚体变换 SE(3)

**CARLA/UE4 坐标系：左手系**，`x` 前、`y` 右、`z` 上；`Location` 单位 **米**，`Rotation` 单位 **度**（`pitch` 绕 y、`yaw` 绕 z、`roll` 绕 x）。左手系下 `yaw` 俯视顺时针为正——**这是和右手系习惯相反的常见坑**。

一个位姿 = `carla.Transform(Location, Rotation)`，数学上是 **SE(3)** 里的刚体变换，可写成 4×4 齐次矩阵：

$$
T=\begin{bmatrix} R & t\\ \mathbf{0}^\top & 1\end{bmatrix},\quad R\in SO(3),\ t\in\mathbb{R}^3,\qquad
\tilde p' = T\,\tilde p,\ \ \tilde p=\begin{bmatrix}p\\1\end{bmatrix}
$$

- $R$ 由欧拉角合成（左手系、按 CARLA 约定 yaw→pitch→roll）；$t$ 是平移。
- **复合**（最常用）：把传感器坐标系下一点变到世界系：

$$
p_{\text{world}} = T_{\text{world}\leftarrow\text{vehicle}}\; T_{\text{vehicle}\leftarrow\text{sensor}}\; p_{\text{sensor}}
$$

挂相机时你给的 `carla.Transform` 就是 $T_{\text{vehicle}\leftarrow\text{sensor}}$（相机相对车体的位姿）。

- **欧拉角缺陷**：万向锁（gimbal lock）；做插值/积分时用四元数更稳——本课用不到，记住即可。

> 落地：`spawn_points[0]` 是一个 `Transform`；`health_check.py` 里 `tf.location.z += 30; tf.rotation.pitch = -45` 就是把 spectator 抬高 30 m、俯角 45°——直接在 SE(3) 位姿上改平移和旋转。

### 4.2 离散时间动力学与固定步长

仿真是 **离散动力系统**：状态按固定步长 $\Delta t$ 更新

$$
x_{k+1}=f(x_k,u_k),\qquad t_k=k\,\Delta t
$$

CARLA 同步模式取 $\Delta t=0.05\text{s}\Rightarrow 20\text{ FPS}$。**为什么必须固定步长**：

1. **可复现**：同 seed、同 $\Delta t$ → 数值积分逐位一致，两次运行轨迹相同（[§7](#7-验收--自测题) 的验收点）。
2. **传感器对齐**：每个 `tick` 所有相机出**同一时刻**的帧，图像与状态不错位（异步下会错帧）。

> 控制频率与决策频率可不同：控制器 20 Hz 跑，VLA 1–2 Hz 查（[§5.3](#53-本项目设计分层--高层离散动作)）。

**$f$ 是什么？= 物理引擎积分。** CARLA 建在 UE 上（UE4 用 PhysX，UE5 用 Chaos）：每 tick 把你的控制 $u_k$（油门/刹车/方向）当成**力**施加（发动机扭矩、刹车、轮胎摩擦、重力、悬挂、碰撞），对运动方程做**数值积分**得 $x_{k+1}$。三个推论：

1. **控制是"踩踏板"不是"设速度"**——速度是物理响应，不是你直接赋值（呼应 [§5.3.1](#531-高层动作--控制器映射表与应急归属) 底层不直接改速度）。
2. **车是完整刚体物理**（参数可改 `VehiclePhysicsControl`）；**行人/walker 常用运动学控制**（直接按方向+速度移动）——这反而方便你**精确编排鬼探头横穿**。
3. **固定 $\Delta t$ + seed → 积分逐步确定 → 可复现**。

### 4.3 闭环 = (PO)MDP 形式化

把驾驶写成 **马尔可夫决策过程** $(\mathcal S,\mathcal A,P,r,\gamma)$：状态 $s_t$、动作 $a_t$、转移 $P(s_{t+1}\mid s_t,a_t)$、策略 $\pi(a\mid s)$。
但**真实驾驶看不到完整状态**（遮挡、传感器有限）→ 是 **POMDP**：只拿到观测 $o_t\sim O(\cdot\mid s_t)$，需对隐藏状态维护信念 $b_t=p(s_t\mid o_{1:t},a_{1:t-1})$。

- **鬼探头 ≡ POMDP 的教科书例子**：公交后的行人是 $s_t$ 里看不见的分量。好策略要在 $o_t$ 不含行人时，仍**根据先验把信念里"可能有人"的概率拉高**并预防性减速。
- **中文指令**就是注入到信念里的外部先验——这把"为什么语言有用"讲成了数学。

### 4.4 分布漂移与复合误差界

设专家策略 $\pi^\*$，学到的策略 $\pi$ 在**专家访问的状态分布** $d_{\pi^\*}$ 下每步犯错概率为

$$
\epsilon=\mathbb E_{s\sim d_{\pi^\*}}\big[\mathbb 1(\pi(s)\neq\pi^\*(s))\big].
$$

- **行为克隆（BC，纯监督）**：闭环代价相对专家的差距界为 $O(\epsilon\,T^2)$ —— $T$ 是 episode 长度。**误差随时间二次增长**：一旦漂出专家分布，进入没有监督的状态，错上加错。（Ross & Bagnell 2010）
- **DAgger（交互式纠正）**：把界改善到 $O(\epsilon\,T)$ —— 线性。（Ross et al. 2011）

直觉：监督学习假设训练/测试同分布，但 **闭环里测试分布是策略自己诱导的** $d_\pi\neq d_{\pi^\*}$（covariate shift）。这是后面采数据（第四课）、选范式（§5.2）的根本约束。

### 4.5 TTC（鬼探头的核心量）

碰撞时间 Time-To-Collision，最常用的一维近似（自车与前方目标同向/对冲）：

$$
\text{TTC}=\frac{d}{\max(v_{\text{closing}},\,0)},\qquad v_{\text{closing}}=v_{\text{ego}}-v_{\text{obj}}
$$

$d$ 为纵向间距，$v_{\text{closing}}$ 为接近速度（>0 才会撞）。鬼探头里行人**突然出现时 $d$ 已经很小**，要使 TTC 仍 ≥ 安全反应时间，唯一办法是**提前把 $v_{\text{ego}}$ 降下来**。项目评测用 `min_ttc`（整段最小 TTC）衡量危险接近程度。

### 4.6 相机投影（点到，第二课展开）

针孔模型：世界点经外参 $[R\mid t]$ 到相机系，再经内参 $K$ 投影到像素：

$$
s\begin{bmatrix}u\\v\\1\end{bmatrix}=K\,[R\mid t]\begin{bmatrix}X\\Y\\Z\\1\end{bmatrix},\quad
K=\begin{bmatrix}f_x&0&c_x\\0&f_y&c_y\\0&0&1\end{bmatrix}
$$

CARLA 相机的 $f$ 由 `image_size_x` 与 `fov` 决定。**第二课挂相机、把 depth 还原成米时会用到**，这里先存档。

## 5. 必须知道的深度学习原理

### 5.1 自动驾驶的学习范式谱系

| 范式                                | 学什么                         | 一句话                           | 代表                              |
| ----------------------------------- | ------------------------------ | -------------------------------- | --------------------------------- |
| **模仿学习 IL / 行为克隆 BC** | 监督拟合专家$(o,a)$          | 简单，但有复合误差（§4.4）      | ALVINN, PilotNet                  |
| **条件模仿 CIL**              | $a=\pi(o,c)$，$c$=导航指令 | **对应本项目的"中文指令"** | Codevilla 2018 (CIL)              |
| **强化学习 RL**               | 用 reward 闭环试错             | 无需专家，但样本贵、sim2real 难  | CARLA RL benchmarks               |
| **端到端 E2E**                | 传感器→控制                   | 黑箱、数据饥渴                   | Bojarski 2016                     |
| **VLA / VLM 驱动**            | 预训练大模型→高层语义动作     | 带常识、可读指令、可 zero-shot   | DriveVLM, LMDrive, GPT-4V on road |

本项目主线 = **CIL 思想 + VLA 实现 + 分层执行**：图像 + 中文指令 → 高层动作（zero-shot 先跑通，进阶再 QLoRA 微调）。

### 5.2 为什么"端到端闭环"难（DL 人尤其要警惕）

1. **协变量偏移（covariate shift）/ 复合误差**：训练分布 ≠ 部署分布；闭环里策略自己诱导状态分布 $d_\pi\neq d_{\pi^*}$，BC 误差 $O(\epsilon T^2)$（见 §4.4）。**解法**：DAgger（专家在策略走偏处补标注，改善到 $O(\epsilon T)$）、恢复数据/数据增强、噪声注入。
2. **因果混淆（causal confusion）**：模型可能学到**相关而非因果**的捷径。经典「惯性问题」——发现"上一帧在刹车"和"这一帧也刹车"高度相关，于是学会复制历史动作而非看路（de Haan 2019；Codevilla 2019《Limitations of BC》）。**给的信息越多，越容易抄捷径**——反直觉但重要。
3. **数据分布长尾**：危险场景（正是鬼探头）在自然数据里极稀有 → 必须**主动造场景采样**（第四课用固定 seed 批量生成）。

→ 这三点正是本项目**不做纯端到端、改用"分层 + 主动造场景 + 高层离散动作"**的理由。

### 5.3 本项目设计：分层 + 高层离散动作

```
图像 + 自车状态(文本) + 中文指令 + 允许动作集
        │  (VLA, 1–2 Hz)
        ▼
   高层动作 ∈ {KEEP_LANE, SLOW_DOWN, STOP, YIELD, FOLLOW, CHANGE_LEFT/RIGHT, TURN_LEFT/RIGHT, NUDGE_AROUND}
        │  (经典控制器, 20 Hz)
        ▼
   carla.VehicleControl(throttle, steer, brake)
```

为什么这么设计（每条都对应一个 DL/控制痛点）：

- **离散高层动作 = 分类而非回归**：动作空间小、标签好定义、模型不易乱给连续值；约束输出到 **允许集合**（结构化输出）可强制合法。
- **解耦语义与控制**：VLA 不必学 PID 级的稳定性，控制器保证不画龙；二者可独立替换/调试。
- **应对大模型延迟**：VLM 闭环延迟约 1–1.5 s，所以**高层 1–2 Hz 查，中间帧由控制器顶住**。这在 RL 里叫**时间抽象 / options（半 MDP）**——高层动作是一个持续若干步的"宏动作"。

#### 5.3.1 高层动作 → 控制器：映射表与「应急」归属

高层动作**不是直接的油门/刹车信号**，它是给底层控制器**设定目标**；控制器再在 20 Hz 把目标变成 `VehicleControl`：

| 高层动作              | 控制器怎么执行                      |
| --------------------- | ----------------------------------- |
| `KEEP_LANE`         | 沿当前车道 waypoint，按默认目标速度 |
| `SLOW_DOWN`         | 调低目标速度                        |
| `STOP`              | 目标速度 0 / 刹车                   |
| `YIELD`             | 有冲突 actor 就停，无则走           |
| `FOLLOW`            | 跟车保持车距（自适应巡航）          |
| `CHANGE_LEFT/RIGHT` | 把目标 waypoint 序列换到左/右车道   |
| `TURN_LEFT/RIGHT`   | 在路口选对应转向的 waypoint 分支    |

所以 `STOP` 落地 = 控制器查表 → 目标速度 0 → 20 Hz 持续发 `brake`，一直到 VLA（1–2 Hz 后）给出新动作。**这就是「低频决策撑起高频控制」的实现：一个高层动作横跨几十个控制帧（options）。**

> **底层是「反馈闭环」，不是「动作回放」**：高层只设**目标**（目标速度/车道），底层每个 tick **重新算**「当前 vs 目标」的偏差，实时输出控制——它边走边修正方向、压车道，而不是播放预先算好的 20 个值。这正是与 action chunking 的本质区别：**chunking 预先吐一段动作来回放（开环）；options 设一个目标让反馈闭环去够（闭环）**（[§5.5(2)](#5-必须知道的深度学习原理)）。底层也**不是直接改速度数值**，而是输出油门/刹车，由物理引擎积分出新速度（见 [§4.2](#42-离散时间动力学与固定步长)）。

> **「应急刹车」不归 VLA。** VLA 是 1–2 Hz，行人**已经窜出**再让它反应，物理上来不及（[§4.5](#45-ttc鬼探头的核心量)）。两条分工要分清：
>
> - **VLA 的价值在「提前」**：还没看见人、但看见「公交车遮挡」时就先 `SLOW_DOWN`（注入 belief 的预防性减速，[§3.1](#31-三层状态为什么纯检测器写不进去)）。
> - **真要做窜出后的硬刹**：那是一个**高频反射层**（基于 TTC 阈值的 rule-based AEB，跑在 20 Hz），可**覆盖**高层动作——属于「快系统」的反射，**不是 VLA**。

### 5.4 VLA / VLM 架构入门（第五课展开）

典型结构：**视觉编码器（ViT）→ 投影层 → LLM 主干**，图像 token 与文本 token 拼接后自回归解码；动作可作为**文本 / 结构化字段 / 专用 action token** 输出。

- **zero-shot**：直接调通用多模态 API（GPT-4V 等），不训练就能跑闭环——本项目第五课先做这个。
- **微调**：用第四课采的数据做 **QLoRA**（4-bit 量化 + 低秩适配），在 16 GB 显存上微调小 VLM（如 Qwen2.5-VL-3B）。
- **结构化/约束输出**：用 JSON schema / 受限解码强制模型只能从允许动作集里选一个，避免自由发挥。

> 本课不需要写任何 VLA 代码，理解"它在栈里的位置 + 输入输出契约"即可。

### 5.5 推理频率、API 现状与「要不要本地推理」

> 本节回答一个常见困惑：**VLA 要做 20 Hz 高频推理还是低频推理？要不要买卡/本地推理？** 答案决定阶段 4 的工程路线，也是本项目「目标与理论」里必须想清的一环。

**(1) 关键区分：推理频率 ≠ 控制频率**

「20 Hz」指的是**控制频率**，不是模型推理频率。自动驾驶的「频率」是分层的：

| 层级                       | 典型频率   | 谁来做                | 本项目对应                                           |
| -------------------------- | ---------- | --------------------- | ---------------------------------------------------- |
| 底层控制（转向/油门/刹车） | 20–100 Hz | 经典控制器（PID/MPC） | 控制器，跟 `fixed_delta_seconds=0.05`（20 Hz）同拍 |
| 轨迹/行为                  | 10–20 Hz  | 规划器                | （本项目简化并入控制器）                             |
| 高层语义决策               | 1–5 Hz    | VLA / VLM             | **VLA 出高层动作**                             |

**没有人让大 VLA 每秒推理 20 次。** 标准做法是**双系统（fast-slow / System 1+2）**：慢的 VLM 大脑 1–5 Hz 做推理，快的控制器在 20 Hz 顶住，两者**异步**运行。代表工作：DriveVLM、Reasoning-VLA、Fast-in-Slow。

**(2) 低频推理怎么撑起高频控制？——两种解耦方式**

| 方式                                       | 机制                                                                             | 用在哪                                                        |
| ------------------------------------------ | -------------------------------------------------------------------------------- | ------------------------------------------------------------- |
| **Action chunking（动作分块）**      | 一次推理吐出**未来一整段连续动作**（如 1 秒 = 50 个），本地逐个高频执行    | 连续控制 VLA：π0 / OpenVLA                                   |
| **高层离散动作 = options（半 MDP）** | 一个高层动作（如 `SLOW_DOWN`）本身**持续若干控制步**，中间帧控制器自己顶 | **本项目**（见 [§5.3](#53-本项目设计分层--高层离散动作)） |

> **本项目用后者，比 chunking 更简单**：`SLOW_DOWN` 这种宏动作天然横跨几十个控制帧——VLA 1–2 Hz 给一次高层动作，控制器 20 Hz 一直执行到下次更新。这正是 §5.3 说的「时间抽象 / options」。**所以你根本不需要 20 Hz 推理。**
>
> **澄清「这还算 VLA / 具身智能吗」**：options vs chunking 只是「低频推理怎么撑高频控制」的**工程手段**，**不决定是不是 VLA**。VLA 的定义是 **Vision + Language → Action**，`STOP`/`SLOW_DOWN` 这种**离散宏动作也是 Action**。在自动驾驶语境里，输出高层语义动作 + 接控制器正是主流范式（DriveVLM / LMDrive，[§5.1](#51-自动驾驶的学习范式谱系)）。本项目**是 VLA，也是具身智能**（仿真环境里闭环地感知—决策—行动）。含金量主要看你做不做 §5.5(8) 的**微调**那一步——那才是「你自己训练的 VLA」。
>
> **动作表示不止这两种，options 也不是"过时技术"**：完整谱系（符号 / 轨迹 / 连续 chunk）、时延陷阱与现代解法、升级路线与 SOTA 坐标见 [§5.8](#58-动作表示谱系时延陷阱与升级路线求职向)。

**(3) 现在有没有「开放的 VLA 推理 API」？**

| 你想要的东西                                           | 现状（2026）                                         | 能用 API 吗               |
| ------------------------------------------------------ | ---------------------------------------------------- | ------------------------- |
| 真·VLA 控制服务（传图 → 直接出油门/方向）            | **无公开商用 API**                             | ❌                        |
| π0 / π0.5（Physical Intelligence）                   | 闭源、仅合作受限，且面向**机械臂操作**不是开车 | ⚠️ 拿不到也不对口       |
| OpenVLA（7B, MIT 开源权重）                            | **只能自己本地部署/自建云**，无官方托管 API    | 本地 ✓ / 公开 API ❌     |
| 通用多模态大模型（GPT-4o / Claude / Gemini / Qwen-VL） | **有成熟 API**                                 | ✅ 但只能当 System 2 大脑 |

结论：**能开放调用的只有通用 VLM API，而它正好胜任本项目的高层语义决策**（看前视图 + 读中文指令 → 吐一个离散高层动作，正是 §5.1 的 DriveVLM / LMDrive 路线）。**真正出控制量的 VLA 没有 API、必须本地。**

**(4) 为什么 API 永远做不了控制环（物理限制）**

带图像的云端多模态 API，单次往返延迟通常 **0.5–2 s**（含网络抖动）= **0.5–2 Hz** 上限。20 Hz 要求 **50 ms** 内返回——**网络物理上做不到**。所以即便将来出现 VLA 控制 API，它也只能放在慢的决策层，**控制环永远必须在本地**。这对本项目不构成约束：本项目要 API 干的恰恰是它最擅长的慢决策。

**(5) CARLA 仿真的「时间红利」**

CARLA **同步模式**（[§2.2](#22-异步-vs-同步先建立概念第二课细做)）下，server **会停下来等你的推理算完**再 `tick`。所以：

> 真实世界里慢 = 撞车；**仿真里慢 = 墙上时钟变慢，但车的行为完全正确**。

⟹ 早期完全可以**用 VLM API 当大脑跑通闭环**，既不卡车也不吃本地显存——这就是阶段 4「先用 prompt/API 做推理」为什么可行、而非权宜之计。

**(6) 单张 16 GB 的现实约束（本项目特有）**

本机只有一张 5070 Ti（16 GB），**CARLA 渲染和本地 VLM 推理要抢同一张卡**（不是「一张管显示 + 一张管推理」的双卡设定）。粗算（**待实测，遵循「先验证后断言」**）：桌面空载 ~2.6 GB + CARLA Low 再吃数 GB ⟹ 留给推理大约 **7–9 GB**。由此三档工作流：

| 工作流                                      | 可行性           | 做法                                                   |
| ------------------------------------------- | ---------------- | ------------------------------------------------------ |
| CARLA +**API** VLA 闭环               | 最稳，无显存争用 | 推理走网络，显存全给 CARLA                             |
| CARLA +**本地 3B VLM** zero-shot 闭环 | 紧但可能可行     | 4-bit 量化，实测剩余显存                               |
| CARLA +**本地 QLoRA 微调** 同时跑     | 基本不行         | 微调离线做（CARLA 关掉）或上服务器（PROJECT_PLAN §7） |

**(7) 结论：要不要本地推理？**

- **阶段 4 起步 = 不需要本地推理**：VLM API 当慢大脑（1–2 Hz）+ 本地经典控制器（20 Hz），最快跑通 pipeline。
- **进阶 = 需要本地**：QLoRA 微调小 VLM（Qwen2.5-VL-3B 级，[§5.4](#54-vla--vlm-架构入门第五课展开)）——这是产出「可控权重、严格可复现」agent 的关键，且**必须离线/服务器做**（见上表第三档）。
- **永久排除**：16 GB 本机硬刚 OpenVLA-7B 微调（官方需 ~27 GB 起）；需要更大算力走服务器路线（PROJECT_PLAN §7），不要外挂老服务器卡。

**(8)「算不算完成」——本项目的四件产物**

本项目核心产物**不是「一个模型」**，而是一个可复现的闭环平台（PROJECT_PLAN §1）。「完成」对应四件：

| # | 产物                                                                | 去哪                 |
| - | ------------------------------------------------------------------- | -------------------- |
| 1 | **平台/框架**（场景生成 + 传感器 + 控制器 + 评测 + 数据管线） | GitHub（主产物）     |
| 2 | **数据集**（图像 + 状态 + 动作标签）                          | HuggingFace Datasets |
| 3 | **微调模型**（QLoRA adapter，进阶阶段产出）                   | HuggingFace Models   |
| 4 | **评测结果**（rule / expert / API-VLA / 微调-VLA 同指标对比） | 报告 / README        |

API 与微调是**两阶段、两个被评测的 agent**，不是二选一：**API（zero-shot）= 起步跑通 + 对照组；本地 QLoRA 微调 = 产出「你自己训练的 VLA」**——后者才是让你能理直气壮说「训练过 VLA」的分水岭，也是简历级亮点（#3 + #4）。

> **复现性边界（关系到本项目「可复现平台」定位）**：API agent 的输出**不严格可复现**（服务端模型版本、采样、限流都不由你控制）。可复现的是**框架**（场景 seed、传感器、指标、数据管线），不是某个 agent。评测时（阶段 5）须**锁定模型版本号、`temperature=0`、把 prompt + 原始响应全量落盘**（可放进 `labels.jsonl`），并在报告里明确区分三档：rule / expert baseline（完全可复现）↔ 本地微调 VLA（可复现）↔ API VLA（版本锁定下近似可复现）。

### 5.6 数据从哪来：专家采集 → 微调数据集 → HF

危险场景在自然数据里是长尾（§5.2），靠随便开采不到 → **主动用脚本造场景、批量采集**。流程（阶段 3→4）：

```
固定 seed 造场景(公交 + 藏在后面的行人 + ego)
   → ego 由"专家"开(BehaviorAgent/规则/手动) ── 专家给出"好动作"当标签
   → 录 ego 第一视角传感器(RGB+depth+semantic) + 车辆状态 + actor metadata + 动作标签
   → 多 episode 攒成数据集 ── 这就是 QLoRA 微调数据 & 可传 HF Datasets(产物 #2)
```

- **开车的是"专家"不是 VLA**（否则循环）：这是**模仿学习/行为克隆（BC）**的数据——"专家这么开，VLA 学着这么决策"。
- **专家从哪来**：CARLA 自带的 `BehaviorAgent`/`TrafficManager` 或你写的规则策略；**没有现成可直接用的"中国式鬼探头专家数据集"，必须自采**。
- 连续控制量要**转成高层离散动作标签**（阶段 3 的活），才能训"图像 + 指令 → 高层动作"。
- 数据格式见 PROJECT_PLAN §8（`frames/` + `*.parquet` + `labels.jsonl`）。

### 5.7 监督学习 vs 模仿学习：数据本质与三个易错点

**(1) BC ≠ 端到端**——两个不同的轴，别混：

| 轴                 | 说的是   | 选项                                            |
| ------------------ | -------- | ----------------------------------------------- |
| **学习方法** | 怎么学   | BC（监督模仿专家）/ RL / …                     |
| **架构**     | 网络结构 | 端到端 E2E（传感器→控制一张网）/ 分层 / 模块化 |

BC 可套在端到端上（PilotNet = BC + E2E），也可套在**高层离散动作**上（本项目）。**"用了 BC" ≠ "端到端"。** 本项目的微调 = **高层动作上的 BC / 条件模仿 CIL**（以中文指令为条件），不是端到端 BC。

**(2) 监督数据 vs 专家（模仿）数据**：

| 维度     | 普通监督学习             | 专家/模仿数据（本项目）                                                                      |
| -------- | ------------------------ | -------------------------------------------------------------------------------------------- |
| 一个样本 | (x, y)，**i.i.d.** | 序列/episode，**非 i.i.d.**（帧间强相关，§1.2）                                       |
| 标签     | 人工标注                 | **专家的动作**                                                                         |
| 分布     | 训练 ≈ 测试             | 训练是$d_{\pi^*}$，部署是策略自己的 $d_\pi$（协变量偏移）                                |
| 存储     | 通常只存 (x, y)          | 存**富录像**（图像 + 全状态 + metadata + 动作），再**派生**出训练用 (输入, 标签) |

**(3) 三个易错点**：

- **协变量偏移**（covariate shift，中文：协变量/输入分布偏移）：策略自诱导分布 → BC 误差 $O(\epsilon T^2)$（§4.4）。解法：DAgger、恢复数据、噪声注入；本项目还靠分层 + 离散动作 + 底层兜稳定来缓解。
- **因果混淆**（causal confusion）：学到相关而非因果的捷径（"刚才在刹车 → 继续刹车"，停下就再起不来）。**给的信息越多越容易抄捷径**（§5.2）。
- **「录 vs 喂」红线**：数据集**全量记录**（含被遮挡 actor 真值，用于算指标/复现/转标签）没问题；但**喂给模型的输入**必须守 [§3.2](#32-特权信息红线什么能喂给决策层什么不能) 红线——**被遮挡 actor 真值绝不能进决策输入**。**记录 ≠ 输入。**

**(4) 专家从哪来**：自采（§5.6）。CARLA 有**专家策略**（BehaviorAgent/TrafficManager）可生成数据，但**没有现成可用的中国式鬼探头数据集**；真实数据集（nuScenes/Waymo）有 sim2real gap 且无你的场景/指令——任务数据必须自己造。

### 5.8 动作表示谱系、时延陷阱与升级路线（求职向）

**(1) 动作表示是一条谱系**，不是"chunking 或不 chunking"二选一：

| 表示                                     | 高层输出什么                                                                   | 谁在用                                                      |
| ---------------------------------------- | ------------------------------------------------------------------------------ | ----------------------------------------------------------- |
| **离散宏动作 / options**（本项目） | 一个符号（`SLOW_DOWN`）                                                      | 分层 VLM-planner（DriveVLM / LMDrive）                      |
| **轨迹 / 路点序列**                | 未来 ~1–3s 一串状态，下游跟踪 +**滚动重规划**（receding horizon / MPC） | **AD 主流端到端**（UniAD、VAD、EMMA、DiffusionDrive） |
| **连续动作分块 chunk**             | 未来一段原始动作（diffusion / flow 生成）                                      | **机器人操作 VLA**（π0、Diffusion Policy、ACT）      |

⟹ **AD 主流其实做"轨迹级 chunking + 滚动重规划"，机器人做"连续动作 chunk"**，我们选最左边的 options 是**图简单**（动作空间小、好调、契合"VLM-API 当大脑"），不是别人不做。

**(2) 时延陷阱：上一轮说的"过时"是"时间上陈旧（stale）"，不是"技术落伍"。** 任何低频决策系统，决策都基于"若干毫秒前的观测"，在保持窗口内是陈旧的——options 和 chunk **都有**这个属性。**现代解法不是放弃时间抽象，而是：**

- **异步 / 实时分块**（Real-Time Chunking；temporal ensembling）：下一段在上一段执行完前就**异步算好、平滑衔接**，永不开环回放陈旧动作。
- **滚动重规划**（receding horizon）：每周期都从**最新状态**重预测，只执行第一小段。
- **底层闭环 + 高频反射层**（本项目）：底层每 tick 按当前状态反馈，AEB 可覆盖（§5.3.1）。

> 所以 options **不是过时技术**——它与 SOTA 共享"时间抽象"内核，差别只在动作表示的丰富度与重规划方式。

**(3) 本项目正踩在一个当前热门架构上**：**双系统 / fast-slow**（慢 VLM 推理 + 快控制器），代表作 GR00T、Helix、Fast-in-Slow、π0.5 的分层。**这是简历上能理直气壮讲的点**（§5.5(1)）。

**(4) 升级路线（MVP 之后能讲的"进阶"）**：

```
v1 离散 options(先跑通)
  → v2 高层改吐"短轨迹/目标路点序列" + 下游 MPC/纯跟踪 + 每周期滚动重规划
  → v3 异步推理(慢 VLM 不阻塞控制) / 轨迹用 diffusion 头
```

每步都让项目更贴 AD SOTA、面试更有的聊；但**别一上来做 v3**——先用 v1 把闭环/场景/评测跑通（§5.5(7)）。

**(5) 面试可复述的坐标**：①动作表示谱系（符号 / 轨迹 / 连续 chunk）②时延陷阱与三种现代解法 ③双系统定位 ④AD SOTA 名字（UniAD / VAD / EMMA / GAIA 世界模型 / DriveVLM / LMDrive）——并能说清**"我们为什么选 options + 升级路线"**。

## 6. 实践：CARLA Python client

### 6.1 API 速查（第一课会用到的最小集）

| 目的            | 调用                                                                        |
| --------------- | --------------------------------------------------------------------------- |
| 连接            | `client = carla.Client(host, port)`；`client.set_timeout(10.0)`         |
| 版本校验        | `client.get_client_version()` / `client.get_server_version()`           |
| 拿世界/地图     | `world = client.get_world()`；`world.get_map()`                         |
| 列地图 / 切地图 | `client.get_available_maps()`；`client.load_world('Town05')`            |
| 观察相机        | `world.get_spectator().set_transform(tf)`                                 |
| 蓝图库          | `bp = world.get_blueprint_library()`；`bp.filter('vehicle.*')`          |
| spawn 点        | `world.get_map().get_spawn_points()`                                      |
| spawn / 销毁    | `world.try_spawn_actor(bp, tf)`（失败返回 `None`）；`actor.destroy()` |
| 自动驾驶        | `vehicle.set_autopilot(True)`                                             |

### 6.2 Actor 生命周期与 cleanup

```python
actors = []
def spawn(world, bp, tf):
    a = world.try_spawn_actor(bp, tf)   # 占位/碰撞会返回 None
    if a is not None:
        actors.append(a)
    return a

def cleanup():
    for a in actors:
        try:
            a.destroy()
        finally:
            pass
    actors.clear()
# 用 try/finally 包主逻辑，确保异常/Ctrl-C 也能清场；否则残留 actor 会让下次 spawn 失败。
```

**任务 1 · 启动 CARLA server**

- **怎么做**：写 `scripts/launch_carla09.sh` = `conda activate carla9` → `cd ~/CARLA/carla-0.9.16` → `./CarlaUE4.sh -quality-level=Low -nosound`；终端1 跑 `bash scripts/launch_carla09.sh`。
- **产出**：`scripts/launch_carla09.sh` + 一个监听 `:2000` 的 server 窗口。
- **验收**：窗口出来不报错；`nvidia-smi` 能看到 CarlaUE4 占显存。
- **坑**：别同时开 0.10.0（都抢 `:2000`）。

**任务 2 · 先跑官方示例（先跑后写）**

> **官方示例 = CARLA 自带的现成 `.py` 脚本**，放在 `~/CARLA/carla-0.9.16/PythonAPI/examples/`，随 CARLA 一起装好——**你只是运行它们，不用自己写**。两个最常用：
> - **`manual_control.py`**：spawn **一辆** ego + 一个 pygame 窗口，你用键盘（WASD/方向键）**开这一辆**车，带 HUD、可切传感器视图。
> - **`generate_traffic.py`**：用 TrafficManager 一次 spawn **很多** NPC 车 + 行人，全开 autopilot（**它们自己跑，你不用管**）。
>
> ⟹ 你说的「生成很多车 + 手动控制」其实是**两个脚本配合**：先用 `generate_traffic.py` 把世界填满车流，再用 `manual_control.py` 在车流里开你自己的车。一个脚本只干一件事。

- **怎么做**：终端2 `conda activate carla9`，进 `~/CARLA/carla-0.9.16/PythonAPI/examples/`，先 `python generate_traffic.py`（造车流，留着跑），再开终端3 `python manual_control.py`（WASD 在车流里开一圈）。
- **产出**：手动开车的体感 + 确认 client↔server 连通（**纯验证：跑现成脚本，不写新文件**）。
- **验收**：能在车流里手动开车转一圈。
- **坑**：client/server 必须都 0.9.16；`manual_control.py` 依赖 `pygame`（carla9 已装，CLAUDE.md §3）。

**任务 3 · 写连接巡检脚本 `health_check.py`**

- **怎么做**：`carla.Client('localhost', 2000)` + `set_timeout(10)`；打印 client/server 版本、当前地图、`get_available_maps()`、blueprint 数；加 `--map Town05` → `load_world('Town05')` + 把 spectator 抬高 30 m / 俯角 45°（[§4.1](#41-坐标系与刚体变换-se3) 的 transform 改平移+旋转）。
- **产出**：`scripts/health_check.py`。
- **验收**：能打印版本/地图/blueprint；`--map Town05` 能切图 + 移 spectator。
- **坑**：`set_timeout` 太短连不上；首次加载大地图慢，timeout 调大。

**最简版（先跑通这十几行，再加 `--map`/spectator）**——每个 `get_*` 都是一次「请求-响应」RPC（[§2.1](#21-server-client--游戏引擎)）：

```python
# health_check.py（最简版）：连上 server，打印基本信息
import carla

client = carla.Client('localhost', 2000)   # ① 连 server 的 RPC 端口(不是真"拿到"server)
client.set_timeout(10.0)                    # ② 每次 RPC 最多等 10 秒响应

print('client 版本:', client.get_client_version())   # 一次 RPC：你问、server 答
print('server 版本:', client.get_server_version())   # 两者必须一致，否则报错诡异

world = client.get_world()                  # ③ 拿到「世界」句柄(远程引用，真世界在 server 里)
print('当前地图:', world.get_map().name)
print('可用地图:', client.get_available_maps())

bp_lib = world.get_blueprint_library()      # ④ 蓝图库(也是远程查询)
print('blueprint 总数:', len(bp_lib))
print('车辆蓝图数:', len(bp_lib.filter('vehicle.*')))
```

> 跑：先按任务 1 起 server，再 `conda activate carla9 && python health_check.py`。
> 把"切地图 + 移 spectator"加上去（`--map` 参数 → `load_world('Town05')` + `world.get_spectator().set_transform(tf)`，`tf` 抬高 30 m、`pitch=-45`），就成了任务 3 的完整 `health_check.py`。

**任务 4 · spawn ego + NPC + cleanup**

- **怎么做**：`blueprint_library.filter('vehicle.*')` 选车；`get_spawn_points()` 取点；`try_spawn_actor`（判空）spawn 1 辆 ego + 几辆 NPC（`set_autopilot(True)`）；用 [§6.2](#62-actor-生命周期与-cleanup) 的 `actors` 列表 + `try/finally` `cleanup()`。
- **产出**：稳定 spawn + 干净销毁（可并进 `health_check` 或独立小脚本）。
- **验收**：spawn ego + N 辆 NPC，结束 `cleanup()` 后**无残留**（重连看不到僵尸 actor）。
- **坑**：spawn point 被占 → 返回 `None`，要判空换点；脚本崩了没 destroy → 下次 spawn 失败。

**任务 5 · 验证二轮车能否 spawn（★项目前提风险）**

- **怎么做**：从 `vehicle.*` 里 filter 出二轮车（`bicycle`/`motorcycle` + 厂商名 `yamaha`/`harley`/`vespa`/`kawasaki`/`crossbike`/`diamondback`/`gazelle`，可参考 CARLA 目录 `my_scripts/list_bikes.py`）；逐个 `try_spawn_actor`，记录每个 blueprint id 成功/失败。
- **产出**：一份「哪些二轮车真能 spawn」的结论。
- **验收**：明确列出**可 spawn 的二轮车 id**（哪怕结论是"某些 spawn 不出来"）。
- **为什么重要**：中国式混合交通全靠二轮车，spawn 不出来项目要改方向（CLAUDE.md §5、PROJECT_PLAN §3.4）；**静态资源存在 ≠ 能 spawn，必须运行时验**（"先验证后断言"）。

**任务 6 · 导出资产清单 `asset_inventory.py` → JSON**

- **怎么做**：遍历 blueprint library，按类别（vehicle / 二轮车 / walker / sensor）整理，把可 spawn 的 actor id（含任务 5 的二轮车结论）导出成结构化 JSON。
- **产出**：`scripts/asset_inventory.py` + `可spawn资产清单.json`。
- **验收**：JSON 结构规整、含二轮车验证结论；后面建场景时能据此选 actor。
- **坑**：JSON/数据不进 git（脚本进 `scripts/`，数据走 `.gitignore`）。

### 6.4 常见坑

- **版本不一致**：client/server 都必须 0.9.16。
- **`set_timeout` 太短** → 连不上；第一次加载大地图慢，timeout 调大。
- **spawn point 被占** → `try_spawn_actor` 返回 `None`（要判空、换点）。
- **actor 残留** → 脚本崩了没 destroy，下次 spawn 失败；重启 server 或先清场。
- **左手系 yaw 方向搞反** → 车头朝向/横穿方向不对（§4.1）。
- **不要同时开 0.9.16 与 0.10.0**：都抢 `:2000`。
